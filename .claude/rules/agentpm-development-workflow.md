# 开发工作流

## 铁律

```
没有验证证据的完成声明 = 谎言
没有 code-reviewer 的代码提交 = 违规
没有技能检查的任务执行 = 违规
```

## 流程（每一步都是强制的）

1. **接收任务**
2. **技能检查** — 扫描触发词，1% 可能性就调用 Skill 工具
3. **实现** — 规范由 hook 自动注入，直接写代码
4. **code-reviewer** — 写完代码立即调用，强制，无例外（涵盖代码质量+安全）。**审查规模自适应（按本轮改动文件数/行数自动决策，无需用户手动触发 /review）**：
   - **可跳过**：纯数据/文案/配置/重命名类小改动（如 seed 数据、i18n、常量），且不触碰敏感路径（认证/权限/数据层/支付）→ 扫一遍 diff 自查即可，不必起 agent。
   - **单次审查**（改动 ≤ 8 文件且 ≤ 400 行）：起一个 code-reviewer，prompt 里明确列出本轮改动文件清单，要求只审这些文件。
   - **自动并行分片**（改动 > 8 文件 或 > 400 行）：**主动按「风险+模块」把文件分成每组 4-8 个，在同一条消息里并行起多个 code-reviewer，各审一组**（流程见 `/review` 命令），最后合并去重报告。墙钟 ≈ 最慢一组，不是串行相加。**这一步是自动的——达到阈值就分片，不要等用户说 /review。**
   - 无论哪种模式：传给 code-reviewer 的都是**本轮改动文件清单**，禁止让它全项目扫描或跑全量 tsc。
   - **执行方式由 `.claude/config.json` 的 `codeReview.mode` 决定，不由你临时判断**：`background`（默认）→ **必须用 Agent 的 `run_in_background:true` 后台启动**，启动后立即继续/结束回合、不阻塞用户，跑完再异步汇报；`blocking` → 当场同步审完再结束回合；`off` → 不审。无论主动调还是被 stop 门禁拦下，都按此 mode 执行——**禁止在 background 模式下前台同步等待审查结果**。
5. **验证** — 运行构建/测试命令，看到输出后才能声明完成
6. **报告结果** — 只有 step 4-5 全部通过后才能向用户报告

## 验证铁律

```
完成声明前必须有新鲜的验证证据。
如果你没有在当前消息中运行验证命令，你不能声称它通过了。
```

| 声明 | 需要的证据 | 不充分的证据 |
|------|-----------|-------------|
| "测试通过" | 测试命令输出：0 failures | 之前的运行、"应该通过" |
| "构建成功" | 构建命令：exit 0 | linter 通过、日志看起来正常 |
| "Bug 已修复" | 复现原始症状：通过 | 代码改了、假设修好了 |
| "需求已满足" | 逐条对照检查清单 | 测试通过 |

## 禁止自动启动项目

禁止自动执行 `npm run dev`、`npm run start:dev`、`vite`、`nest start`、`docker compose up` 等启动/常驻项目的命令。项目由用户自行启动。
